# 백로그: 사용자당 "방송 준비 중" 상한 (#212)

- **형식**: User Stories
- **만든 방법**: `/pm-execution:write-stories`. 이슈 #212(보안 감사 run-1, 독립 검증자 재현)와 `docs/PRD.md` §7.4 "목록 노출"·§8.2를 근거로 했다.
- **실사용자 데이터 없음**. 근거는 감사 재현 결과(100회 생성 뒤 기본 목록 `{victim:LIVE 1, attacker:READY 99}`)와 공유 테스트 계정으로 심사하는 공모전 조건이다.
- **크기 판단**: 방향이 정해진 기능. DB 스키마는 그대로이고, 기존 `POST /api/broadcasts`에 거부 응답(409) 하나가 붙는다.

## 정한 것

| 항목 | 값 | 근거 |
|---|---|---|
| 상한 N | 10 | 공개 목록 100행 중 한 계정 몫을 10%로 묶는다. 심사위원 여럿이 테스트 계정 하나를 나눠 쓰다 버린 방송 준비 중이 쌓여도 바로 막히지 않게 너무 낮게 두지 않았다. |
| 세는 대상 | 호출자의 `READY` 중 만든 지 24시간(`READY_LISTED_MS`) 안인 것 | 공개 목록에 "방송 준비 중"으로 오르는 행과 같은 조건이다(§7.4). 24시간이 지난 READY, 삭제한 방송, LIVE·ENDED는 세지 않는다. |
| 거부 응답 | 409 + 사용자용 문구 | "1인 1 LIVE"와 같은 방식(§7.4). 횟수 제한이 아니라 지금 가진 방송 수 때문이라 429가 아니다. |
| 목록 정책 | 바꾸지 않는다 | 한 사용자의 READY가 목록에 N개를 넘을 수 없으므로 목록 쪽 스트리머당 노출 상한은 따로 두지 않는다. §7.4 순서·24시간 노출, §8.2 고정 100행 상한(페이지네이션 없음)은 그대로다. |

## Stories

#### Story 1: 반복 생성 거부
**스트리머로서, 공개 목록에 오른 내 방송 준비 중이 10개면 새 방송 만들기가 거부되기를 원한다. 그래야 한 계정이 공개 목록을 채울 수 없다.**

Acceptance Criteria:
- [ ] 만든 지 24시간 안인 READY가 10개인 사용자의 `POST /api/broadcasts`는 409이고 방송을 저장하지 않는다.
- [ ] 9개일 때는 201로 만들어진다.
- [ ] 동시에 여러 요청을 보내도 READY가 10개를 넘지 않는다.
- [ ] 하나를 삭제하거나 하나가 24시간을 넘기면 다시 만들 수 있다.
- [ ] 다른 사용자의 READY 수는 내 상한에 영향을 주지 않는다.

Priority: P0 | Effort: S | Dependencies: none

---

#### Story 2: 다른 사용자의 행이 목록에 남는다 (회귀)
**시청자로서, 한 계정이 방송을 계속 만들어도 다른 스트리머의 방송 준비 중과 방송 종료를 홈 목록에서 보고 싶다.**

Acceptance Criteria:
- [ ] 한 사용자가 생성을 상한 넘게 반복한 뒤에도 다른 사용자의 READY·ENDED 행이 `GET /api/broadcasts`(전체)에 남는다.
- [ ] `?status=READY` 탭에도 다른 사용자의 READY가 남는다.
- [ ] 목록 순서(LIVE → READY → ENDED)와 100행 상한은 그대로다.

Priority: P0 | Effort: S | Dependencies: Story 1

---

#### Story 3: 상한에 걸렸을 때 화면 안내
**스트리머로서, 방송 만들기가 거부되면 이유와 할 일을 알고 싶다. 그래야 쓰지 않는 방송을 지우고 다시 만들 수 있다.**

Acceptance Criteria:
- [ ] 방송 만들기 화면(`/studio/new`)이 409를 받으면 API가 보낸 문구를 폼 오류로 그대로 보인다(`apps/web/CLAUDE.md` "`ApiError.serverMessage`" 규칙).
- [ ] 문구는 "방송 준비 중인 방송은 10개까지 둘 수 있습니다. 내 방송에서 쓰지 않는 방송을 삭제한 뒤 다시 만들어 주세요."다(존댓말 평서문, GLOSSARY 용어).
- [ ] 폼에 입력한 값은 지워지지 않는다.

Priority: P1 | Effort: S | Dependencies: Story 1

### Technical Notes

- 확인과 insert 사이 경쟁: 한 트랜잭션에서 사용자별 advisory lock(`pg_advisory_xact_lock`)을 잡고 센 뒤 insert한다. 잠금 없이 세면 병렬 요청이 모두 9개를 보고 통과한다.
- 연결 점유: 같은 사용자의 생성은 `ConfirmGate`(#215)로 연결을 잡기 전에 줄 세우고, 전체는 3개(`CREATE_CONCURRENCY`)까지만 transaction에 들인다. 잠금을 기다리는 요청이 공유 pool(10개) 연결을 쥐면 한 사용자의 연타가 다른 사용자를 막는다.
- 세는 쿼리는 기존 인덱스 `@@index([streamerId, createdAt])`를 탄다. 마이그레이션은 없다.
- 시각은 목록과 같은 주입 시계(`CLOCK`)로 계산한다.

### Open Questions

- 계정 여러 개(가입 비용이 낮다)로 나눠 만드는 경우는 막지 않는다. 가입 횟수 제한은 이 이슈 범위 밖이다.
- 스팸 행을 지울 관리자 경로는 여전히 없다(이슈 본문 지적). 운영자가 DB에서 지운다.
