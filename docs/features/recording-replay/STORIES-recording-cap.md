# 백로그: LIVE 녹화 용량 상한 (#209, #148)

- 형식: 사용자 스토리
- 스토리 수: 5
- 크기 판정: 방향이 이슈에 정해져 있고 DB·API가 바뀌지 않는다(`docs/agents/pm-skills.md` "방향이 정해진 기능" 행). 그래서 `/pm-execution:write-stories`만 쓴다.
- 근거: 실사용자 데이터 없음. 근거는 보안 감사 run-1 재현 결과(#209), PRE-MORTEM T19, `docs/OPERATIONS.md` "녹화 파일"의 용량 추정(1시간 방송 약 1~2GB)이다.

## 배경

녹화 정리 작업(`RecordingReconciler`, 30초 주기)은 녹화 폴더 전체가 `RECORDINGS_MAX_GB`를 넘으면 ENDED 방송의 녹화만 오래된 것부터 지운다. LIVE 녹화에는 길이·크기 상한이 없다. 그래서 LIVE 녹화 하나가 상한을 넘기면 다른 사용자의 다시보기가 모두 지워지고, 그래도 LIVE 녹화는 계속 쓰인다.

## 스토리

### 스토리 1: 송출 중 녹화만으로 상한을 넘으면 녹화를 멈춘다
**다른 스트리머로서, 누군가의 긴 방송 때문에 내 다시보기가 지워지지 않기를 원한다. 그래야 끝난 방송을 계속 보여 줄 수 있다.**

수락 기준:
- [ ] LIVE 방송 녹화 폴더 크기의 합이 `RECORDINGS_MAX_GB`를 넘으면, 정리 작업이 그 LIVE 방송들의 녹화 작업에 `stopRecording`을 부른다.
- [ ] 이때 ENDED 방송의 녹화 폴더와 `recordingFiles`는 그대로 남는다(지워도 상한 아래로 못 내려가므로).
- [ ] 송출과 시청은 끊지 않는다. 방송 상태는 LIVE 그대로다.
- [ ] API 로그에 어느 방송의 녹화를 왜 멈췄는지 남는다.

우선순위: P0 | 크기: S | 의존: 없음

### 스토리 2: 상한을 넘은 동안 녹화를 다시 켜지 않는다
**운영자로서, 멈춘 녹화가 다음 주기에 다시 켜지지 않기를 원한다. 그래야 디스크가 계속 차지 않는다.**

수락 기준:
- [ ] 스토리 1·3의 조건에 걸린 LIVE 방송은 녹화 작업이 없어도 정리 작업이 `startRecording`을 부르지 않는다.
- [ ] 같은 방송이 유예 시간 안에 다시 연결돼도 조건이 그대로면 녹화를 다시 켜지 않는다.
- [ ] 조건에 걸리지 않은 LIVE 방송은 지금처럼 녹화 작업이 없으면 다시 켠다.

우선순위: P0 | 크기: S | 의존: 스토리 1

### 스토리 3: 방송 하나의 녹화 크기·시간에 상한을 둔다
**다른 스트리머로서, 방송 하나가 저장 공간 전체를 차지하지 않기를 원한다. 그래야 오래 방송한 사람이 있어도 다른 다시보기가 남는다.**

수락 기준:
- [ ] LIVE 방송 하나의 녹화 폴더가 `RECORDINGS_MAX_GB_PER_BROADCAST`(기본 3GB) 이상이면 그 방송의 녹화를 멈춘다.
- [ ] LIVE가 된 지 `RECORDINGS_MAX_HOURS_PER_BROADCAST`(기본 3시간) 이상 지나면 그 방송의 녹화를 멈춘다.
- [ ] 방송당 크기 상한이 전체 상한보다 크게 설정되면 전체 상한을 쓴다.
- [ ] 두 값은 양수가 아니면 API가 시작할 때 거부한다.

우선순위: P1 | 크기: S | 의존: 스토리 2

### 스토리 4: 운영 문서가 새 동작을 설명한다
**운영자로서, 녹화가 왜 멈췄는지 문서로 알 수 있기를 원한다.**

수락 기준:
- [ ] `docs/OPERATIONS.md` "녹화 파일", README 환경 변수 표, `.env.example`, `deploy/compose.yaml`에 새 변수와 동작이 있다.
- [ ] `RECORDINGS_DIR`을 크기 제한된 별도 파일시스템에 두는지는 "운영 조치 필요"로 PR에 남긴다.

우선순위: P1 | 크기: S | 의존: 스토리 1~3

### 스토리 5: 다시보기 화면에 녹화가 중간까지만 있음을 보여 준다 (#148 두 번째 기준)
**시청자로서, 다시보기가 방송 도중에 끝나는 이유를 알고 싶다.**

수락 기준:
- [ ] 녹화를 상한으로 멈춘 방송의 다시보기에 "녹화가 중간까지만 저장됐다"는 안내가 보인다.

우선순위: P2 | 크기: M | 의존: 스토리 1~3. 멈춘 사실을 저장할 DB 컬럼이 필요하다. 이번 작업(#209)에는 넣지 않고 #148에 남긴다.

## 기술 메모

- 판정은 디스크 상태와 방송 행에서 매 주기 새로 계산한다. LIVE 녹화 크기와 경과 시간은 줄지 않으므로 별도 상태 저장 없이도 멈춘 녹화가 계속 멈춰 있다.
- `planRecordings`가 멈출 LIVE 방송 목록(`stopLive`)을 따로 돌려주고, 정리 작업은 파일을 먼저 읽은 뒤 녹화 작업을 맞춘다.
- 송출 허가(`goLive`)의 즉시 녹화 시작은 그대로 둔다. 디스크를 읽으면 OME의 3초 응답 제한에 걸릴 수 있다. 상한 초과 중 새로 시작한 녹화는 다음 주기(최대 30초)에 멈춘다.
