## Product Requirements Document: 채팅 도배 방지

**Author**: kh.jeon

배경 논의: [`DISCOVERY-chat-flood.md`](./DISCOVERY-chat-flood.md), [`RED-TEAM-chat-flood.md`](./RED-TEAM-chat-flood.md). 실사용자 데이터 없음. 근거는 보안 감사 run-1 재현과 치지직·Twitch의 공개 동작이다.

### 1. Summary

한 계정이 보낼 수 있는 채팅·댓글 수를 짧은 창마다 묶고, 시청자는 처음 들어올 때 최근 채팅만 받는다. 실시간 화면은 들고 있는 메시지 수에 상한을 두고, 다시보기는 재생 위치를 따라 필요한 만큼만 이어 받는다.

### 3. Background

- 감사 재현: 한 계정이 보낸 채팅 2000개가 모두 받아들여졌다. 새 시청자는 GET 11회로 2000개를 모두 받고 모두 그렸다. 그 기록은 다시보기에도 남는다.
- 지울 방법은 방송 전체 삭제뿐이다. 소유자 채팅 삭제는 PRD §7.5가 미뤘다.
- 같은 문제가 로그인·회원가입·검색에는 이미 `ThrottlerGuard`로 막혀 있다. 채팅·댓글 생성만 빠졌다.

### 4. Objective

한 계정이 방송 채팅을 메시지로 덮지 못하게 하고, 새 시청자의 첫 로드가 채팅 총량과 무관하게 한 번의 작은 요청으로 끝나게 한다.

**Key Results** (인수 기준으로 대신한다)
- 한 계정이 창 안에서 N+1번째 채팅·댓글을 보내면 429를 받는다(e2e). 다른 계정은 영향이 없다.
- 시청자 첫 로드가 최근 50개만 받는다(요청 1회).
- 실시간 채팅 화면이 들고 있는 메시지는 200개를 넘지 않는다.
- 다시보기에서 재생 위치 ±3초 동기화(#92)가 그대로다. 재생 위치에 닿기 전 메시지는 받지 않는다.

### 5. Market Segment(s)

- **시청자**: 방송 중 채팅을 읽고 쓴다. 도배가 오면 대화가 묻힌다.
- **도배 계정**: 로그인한 사용자 하나. 계정을 여러 개 만드는 것은 회원가입 한도(IP당 20개/시간)가 묶는다.
- **심사위원**: README 절차대로 채팅·댓글을 몇 개 쓴다. 정상 사용이 429를 받으면 안 된다.

### 6. Value Proposition(s)

**시청자**
- **Who**: 방송 중이나 다시보기에서 채팅을 보는 시청자
- **Why**: 대화를 읽고 싶다
- **What before**: 한 계정이 수천 개를 보내면 화면이 그 메시지로 차고, 들어올 때 전부 내려받는다
- **How**: 계정마다 10초에 10개까지, 입장 시 최근 50개, 화면에 200개까지
- **What after**: 도배 속도가 1초 1개로 묶이고, 입장이 빠르다
- **Alternatives**: 방송 전체 삭제(유일한 정리 방법)

**채팅을 보내는 시청자**
- **Who**: 빠르게 여러 번 보내다 한도에 걸린 사람
- **Why**: 왜 안 보내지는지 알고 싶다
- **What before**: (한도 없음)
- **How**: 429면 입력창 아래에 "채팅을 너무 빠르게 보내고 있습니다. 잠시 후 다시 보내 주세요." 초안은 남는다
- **What after**: 잠시 뒤 그대로 다시 보낸다
- **Alternatives**: 없음

### 7. Solution

#### 7.1 API

- `POST /broadcasts/:id/chat`: `LoggedInGuard` 다음에 `UserThrottlerGuard`. 추적 키는 세션 사용자 id. 한도 `CHAT_RATE_LIMIT = { limit: 10, ttl: 10_000 }`. 넘으면 429.
- `POST /broadcasts/:id/comments`: 같은 가드, `COMMENT_RATE_LIMIT = { limit: 5, ttl: 60_000 }`. 댓글은 방송 후 감상이라 더 느리다.
- `GET /broadcasts/:id/chat?latest=true`: 가장 최근 `CHAT_LATEST_LIMIT = 50`개를 오래된 순으로. `after`와 함께 오면 400. `latest`가 없으면 지금처럼 처음부터 200개씩(다시보기가 쓴다).
- 한도 저장소는 프로세스 메모리(기존 throttler와 같다). API는 한 프로세스다(`deploy/compose.yaml`).
- 후원 줄(#166)은 결제 확인 경로가 넣으므로 한도와 무관하다.

#### 7.2 웹

- 실시간(`ChatPanel`): cursor가 없으면 `latest=true`로 묻고, 그다음부터 `after`. 즉시 이어 읽기는 `after` 페이지가 꽉 찼을 때만. 들고 있는 메시지는 `CHAT_HELD_LIMIT = 200`개, 넘으면 오래된 것부터 버린다(cursor는 그대로).
- 다시보기(`ChatHistory`): 처음부터 한 페이지 받고, 재생 위치가 받은 마지막 메시지에 닿으면 다음 페이지를 받는다. 요청은 겹치지 않는다. 재생 위치를 모르면(시작 시각 없는 녹화, 재생 전) 첫 페이지를 보이고, 끝이 아니면 "채팅 더 보기" 버튼으로 이어 받는다. 그리는 줄은 마지막 200개.
- 429 문구는 채팅 입력창과 댓글 입력창 모두.

#### 7.3 Assumptions and open questions

- (가정) 정상 사용은 10초 10개를 넘지 않는다. 상수 한 곳에서 바꾼다.
- (가정) 다시보기에서 이미 받은 메시지는 버리지 않는다. 뒤로 탐색해도 다시 받지 않기 위해서다. 받는 양은 재생 위치까지로 묶인다.
- (열림) 소유자 채팅 삭제·차단. PRD §7.5대로 이 문서 밖이다.
