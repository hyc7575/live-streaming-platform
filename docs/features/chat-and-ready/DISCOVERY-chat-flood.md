# Discovery Plan: 채팅 도배 방지 (#213)

**Date**: 2026-11-17
**Product Stage**: existing (공모전 제출물, 마감 2026-11-19)
**Discovery Question**: 한 계정이 채팅을 덮지 못하게 하면서 정상 시청자의 채팅·다시보기 경험을 깨지 않으려면 무엇을 얼마나 해야 하나?

실사용자 데이터 없음. 근거는 보안 감사 run-1 재현 결과(한 계정 2000개 전송이 모두 받아들여지고, 새 시청자가 GET 11회로 2000개를 받음), 치지직·Twitch의 공개 동작(채팅 속도 제한, 입장 시 최근 메시지만 보임, 화면에 남는 줄 수 제한)이다.

## 현재 상태

- `POST /broadcasts/:id/chat`: `LoggedInGuard`만 있다. 횟수 제한이 없다. 댓글 생성도 같다.
- `GET /broadcasts/:id/chat`: `after`가 없으면 가장 오래된 것부터 200개. 클라이언트는 꽉 찬 페이지 뒤에 바로 이어 받아 끝까지 읽는다.
- `ChatPanel`(실시간)·`ChatHistory`(다시보기)가 받은 메시지를 모두 렌더링한다. 다시보기는 재생 위치까지 보낸 메시지만 거른다(#92).

## Selected Ideas for Validation

1, 4, 5, 6, 7, 8. 이슈 #213이 정한 방향이고 DB 변경이 없다.

- 2는 고르지 않는다: 한 NAT 뒤 여러 시청자(심사장 와이파이)를 같이 막는다. 채팅은 로그인이 필요하므로 userId가 더 정확하다.
- 3은 고르지 않는다: 본문만 바꾸면 우회된다. 1이 같은 효과를 더 단순하게 낸다.
- 9는 PRD §7.5가 미뤘다. 이 이슈 범위 밖이다(필요하면 새 이슈).
- 10은 방송 설정 UI·DB가 필요하다. 마감 안에 비용이 크다.

## Decision Framework

- E1·E2·E3 통과 → PRD-chat-flood로 확정하고 구현을 머지한다.
- E3가 실패(동기화 깨짐) → 다시보기는 기존처럼 전체를 받고 렌더링 상한만 둔다.
- 심사·리허설에서 정상 사용이 429를 받는다 → 상한을 올린다(상수 한 곳).
