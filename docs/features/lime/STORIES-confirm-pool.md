# 결제 확정이 공유 DB 연결을 붙잡지 않게 한다 (#215)

**형식**: User Stories
**스토리 수**: 4
**근거**: 실사용자 데이터 없음. 근거는 #215 로컬 재현(아래)과 보안 감사 run-1.

## 배경

라임 충전 확정(`POST /api/lime/charges/confirm`)과 카드 후원 확정(`POST /api/donations/confirm`)은 transaction 안에서 주문 행을 `FOR UPDATE`로 잠근 채 Toss 승인 응답을 기다린다. transaction 하나가 공유 `pg.Pool`(max 10)의 연결 하나를 그동안 쥔다. 이 pool은 세션 저장소와 모든 Prisma 쿼리가 함께 쓴다.

로컬 재현(Toss stub 300 ms 뒤 404, 자기 DB, main `158aaaf`)에서 측정한 값:

| 경우 | 공격 중 무관한 사용자 `GET /api/auth/me` 최대 | A 응답 |
|---|---|---|
| 한 사용자, 주문 40개 동시 확정 | 1209 ms (평소 2~4 ms) | 400 ×40 |
| 한 사용자, 같은 주문 20개 동시 확정 | 4831 ms | 400 ×16, 500 ×4 |

같은 주문이면 행 잠금을 기다리는 transaction도 연결을 쥐고 줄을 선다. 그래서 더 나쁘다.

## 범위

- 한다: 사용자별 확정 직렬화, 확정 전체 동시 상한, 사용자별 요청 제한, pool의 연결 대기 시간 제한.
- 하지 않는다: Toss 호출을 행 잠금·transaction 밖으로 빼기. 확정 흐름을 다시 짜는 일이다. 같은 Idempotency-Key 동시 요청에 Toss가 어떻게 답하는지는 Toss를 불러야 알 수 있다. #197 사전 부검은 제출 전 No-Go였다. 제출 뒤 #197과 함께 본다.

## Stories

#### Story 1: 한 사용자의 확정은 한 줄로 선다
**시청자로서, 다른 사람이 결제 확정을 연달아 보내도 내 화면이 느려지지 않기를 원한다. 그래야 방송을 끊김 없이 볼 수 있다.**

수락 기준:
- [ ] 같은 사용자의 확정(라임 충전·카드 후원 합산)은 한 번에 하나만 transaction에 들어간다. 나머지는 연결을 잡지 않고 앞의 것이 끝나기를 기다린다.
- [ ] 같은 주문의 동시 확정(새로고침, 두 탭)은 지금처럼 Toss를 한 번만 부르고, 모두 같은 결과를 받는다(`lime.e2e`·`donations.e2e` 동시 확정 테스트 통과).
- [ ] 앞의 확정이 실패해도(400, 502, 예외) 다음 확정이 이어서 들어간다.
- [ ] 한 사용자가 같은 주문으로 확정 40개를 동시에 보내도, 다른 사용자의 `GET /api/auth/me`가 1초 안에 200을 받는다.

Priority: P0 | Effort: S | Dependencies: 없음

---

#### Story 2: 확정 전체가 쓰는 연결 수에 상한이 있다
**시청자로서, 여러 계정이 동시에 결제를 확정해도 사이트의 나머지 기능이 돌기를 원한다. 그래야 결제 몰림이 시청을 막지 않는다.**

수락 기준:
- [ ] 서로 다른 사용자의 확정이 동시에 많아도, Toss 응답을 기다리는 확정은 최대 3개다(`CONFIRM_CONCURRENCY`). pool 10개 중 7개 이상이 늘 다른 요청에 남는다.
- [ ] 상한을 넘은 확정은 거절되지 않고 차례를 기다린다(심사위원의 정상 결제가 실패하지 않는다).
- [ ] 상한은 프로세스 하나 기준이다(API 컨테이너는 하나).

Priority: P0 | Effort: S | Dependencies: Story 1과 같은 module

---

#### Story 3: 확정 요청 수에 사용자별 제한이 있다
**운영자로서, 한 계정이 가짜 결제 키로 확정을 끝없이 보내 Toss 호출과 서버 자원을 쓰지 못하게 하고 싶다.**

수락 기준:
- [ ] 같은 사용자의 확정 요청은 1분에 20개까지다(라임 충전과 카드 후원 각 라우트). 넘으면 429이고 Toss를 부르지 않는다.
- [ ] 제한은 IP가 아니라 로그인 사용자 기준이다. 다른 사용자는 영향받지 않는다.
- [ ] 로그아웃한 호출자는 지금처럼 401을 먼저 받는다.
- [ ] 성공 페이지를 몇 번 새로고침하는 정상 사용은 제한에 걸리지 않는다.

Priority: P1 | Effort: S | Dependencies: 없음

---

#### Story 4: DB 연결을 무한정 기다리지 않는다
**시청자로서, DB 연결이 모자랄 때 요청이 끝없이 매달리지 않고 오류로 끝나기를 원한다. 그래야 다시 시도할 수 있다.**

수락 기준:
- [ ] 공유 pool에 `connectionTimeoutMillis`(5초)를 준다. 연결을 5초 안에 못 얻은 요청은 오류로 끝난다.
- [ ] pool 크기(`max`)를 코드에 10으로 적어 두어, 기본값에 기대지 않는다.
- [ ] 기존 e2e가 모두 통과한다.

Priority: P1 | Effort: S | Dependencies: 없음

## Story Map

- 해야 함: Story 3, Story 4 (양과 최악의 대기에 상한)

## Technical Notes

- API 모양은 바뀌지 않는다. 확정 라우트에 429가 생길 뿐이다. DB 스키마 변경 없음.
- 직렬화·상한은 메모리 안의 gate다. API 프로세스가 여럿이 되면 프로세스마다 따로 센다.
- Toss stub은 env로 바꿀 수 없다(`HttpTossPayments`의 base URL은 상수). 테스트는 `FakeTossPayments` provider override를 쓴다.
