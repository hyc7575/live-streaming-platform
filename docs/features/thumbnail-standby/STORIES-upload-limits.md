# 백로그: 이미지 업로드 본문 한도 (#211)

`/pm-execution:write-stories`로 만들었다. 실사용자 데이터 없음, 근거는 보안 감사 run-1 검증 결과(1 MiB 텍스트 필드 32개가 200으로 처리되고 heap이 16 MB에서 111 MB로 오름)와 이슈 #211이다.

- 형식: 사용자 스토리
- 스토리 수: 3
- 크기 판단: 방향이 정해진 기능이다. 고칠 방향이 이슈에 있고, DB와 API 모양은 바뀌지 않는다. 정상 클라이언트(웹)는 `image` 파일 파트 하나만 보내므로 거절이 늘어도 화면 동작은 같다.

대상 라우트: `PUT /api/me/avatar`, `PUT /api/me/standby-image`, `PUT /api/broadcasts/:id/thumbnail`. 세 라우트 모두 `apps/api/src/images/image-rules.ts`의 `ImageUpload()`를 쓴다.

## 스토리

### 스토리 1: 텍스트 필드가 붙은 업로드를 파싱 단계에서 거절한다

**시청자와 방송자로서, 한 사용자가 이미지 업로드에 큰 텍스트 필드를 붙여 보내도 API가 그 내용을 메모리에 쌓지 않기를 원한다. 그래야 채팅·결제·송출 승인이 계속 동작한다.**

수락 기준:
- [ ] 세 라우트 모두 `image` 파일 파트 외에 텍스트 필드가 하나라도 있으면 400을 돌려준다.
- [ ] 400 응답의 `message`는 그 라우트의 기존 "이미지가 유효하지 않음" 문구(`IMAGE_RULES[kind].invalidMessage`)와 같다.
- [ ] 거절된 요청은 저장된 이미지를 바꾸지 않는다.
- [ ] 텍스트 필드 없이 파일 하나만 보낸 정상 업로드는 지금처럼 성공한다.

우선순위: P0 | 크기: S | 의존: 없음

### 스토리 2: multipart 파트·헤더 수를 고정한다

**운영자로서, 이미지 라우트의 multipart 한도가 모두 유한하기를 원한다. 그래야 필드 대신 다른 파트나 헤더를 늘려 메모리를 쓰는 길도 막힌다.**

수락 기준:
- [ ] `limits`에 `fields: 0`, `parts: 1`, `files: 1`, 작은 `fieldSize`, `fieldNameSize`, `headerPairs`가 모두 있다.
- [ ] 파일 파트를 두 개 보내면 400과 같은 문구를 돌려준다.
- [ ] 한도 오류(multer `LIMIT_*`)는 모두 400과 같은 문구로 바뀌고, 영어 multer 문구가 응답에 나오지 않는다.

우선순위: P0 | 크기: S | 의존: 스토리 1

### 스토리 3: Caddy `/api/*`에 본문 크기 상한을 둔다

**운영자로서, API 앞의 프록시가 가장 큰 이미지 규칙보다 조금 큰 본문까지만 넘기기를 원한다. 그래야 API가 multer 한도를 보기 전에 큰 본문이 걸러진다.**

수락 기준:
- [ ] `deploy/Caddyfile`의 `handle /api/*`에 `request_body { max_size … }`가 있다.
- [ ] 상한은 가장 큰 이미지 규칙(2 MiB) + multipart 오버헤드보다 크다(4 MiB).
- [ ] 운영 서버 반영은 PR 본문에 "운영 조치 필요"로 적는다. 이 작업은 운영 서버를 바꾸지 않는다.

우선순위: P2 | 크기: S | 의존: 없음

## 스토리 맵

- 필수: 스토리 1, 스토리 2 (이슈 완료 조건)
- 있으면 좋음: 스토리 3 (이슈의 "선택" 항목, 다층 방어)

## 기술 메모

- Nest `transformException`은 `LIMIT_FILE_SIZE`를 413, 나머지 `LIMIT_*`를 영어 문구의 400으로 바꾼다. 기존 `FileTooLargeFilter`처럼 업로드 인터셉터의 오류를 라우트 문구의 400으로 통일한다.
- 필터는 라우트 전체에 걸리므로 서비스가 던지는 다른 400 문구를 덮지 않도록 multer에서 온 오류만 바꾼다.
- `fields: 0`이면 `fieldSize`는 쓰이지 않지만 다른 설정이 바뀌어도 상한이 남도록 작게 둔다.
