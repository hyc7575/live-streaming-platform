# 백로그: 내장 TURN 중계 범위 확인 (#216)

- 형식: Job Stories
- 출처: 보안 감사 run-1 "확인 필요" 항목, 이슈 #216
- 실사용자 데이터 없음. 근거는 감사 원본(`NEEDS-VALIDATION.md`)과 OME v0.21.0 동작이다.
- 크기: 이슈가 확인 방법과 고칠 방향을 정했고 DB·API가 바뀌지 않아 "방향이 정해진 기능" 행으로 정했다.

## 스토리

### 스토리 1: 격리 스택에서 TURN 중계 여부를 판정한다 (스파이크)

**운영자로서 3478/tcp가 인터넷에 열려 있을 때, OME 내장 TURN이 임의 peer로 바이트를 넘기는지 알고 싶다. 그래야 내부 서비스(postgres, api, OME 관리 API)가 TURN 뒤에서 노출되는지 판단할 수 있다.**

수락 기준:
- [ ] 공유 `lsp-ome-1`이 아닌 별도 compose 프로젝트의 internal 네트워크에서 `ovenmediaengine:v0.21.0`을 저장소 `ome/Server.xml`로 띄운다.
- [ ] 같은 네트워크의 더미 TCP·UDP 리스너를 peer로, 기본 계정 `ome`/`airen`으로 Allocate → CreatePermission → ChannelBind → ChannelData·Send, RFC 6062 Connect를 시도한다.
- [ ] 각 요청의 STUN 응답(성공·오류 코드)과 더미 리스너 수신 바이트 수를 기록한다.
- [ ] 리스너가 바이트를 받으면 "확인", 거부되거나 수신이 없으면 "반박"으로 판정한다.
- [ ] 실험 뒤 컨테이너·네트워크를 지운다. 외부 주소로는 TURN을 보내지 않는다.

우선순위: P0 | 크기: S | 의존: 없음

수락 기준:

- [ ] `docs/features/publish/`(README와 SCENARIOS)에 판정과 재현 스크립트 위치(`scripts/turn-relay-check/`)를 남긴다.
- [ ] 반박이면 이슈를 닫는다.

우선순위: P0 | 크기: S | 의존: 스토리 1

### 스토리 3: (확인 시 필수, 반박 시 선택) ome를 DB와 다른 네트워크로 둔다

**운영 compose를 배포할 때, TURN이나 OME 취약점으로 ome 컨테이너가 뚫려도 postgres에 바로 닿지 않기를 원한다. 그래야 피해가 미디어 서버에서 멈춘다.**

수락 기준:
- [ ] 운영 compose에서 ome는 postgres·db-backup과 같은 네트워크에 있지 않다.
- [ ] api는 ome 관리 API(8081)와 admission 경로(ome → api:3000)를 그대로 쓴다.
- [ ] Caddy는 ome 시그널링·LL-HLS(3333)를 그대로 중계한다.
- [ ] 녹화 폴더 공유(호스트 볼륨)는 네트워크와 무관하므로 바뀌지 않는다.
- [ ] `docker compose config`가 통과하고, 격리 스택에서 ome → postgres:5432 연결이 실패한다.

우선순위: 확인 시 P0, 반박 시 P2 | 크기: S | 의존: 스토리 1

## 기술 메모

- 운영 compose 변경은 배포에 영향을 준다. PR을 열고 머지 전에 coordinator에게 묻는다.
- TURN 계정 변경(기본 `ome`/`airen`)은 PRD §7.2가 미결로 남긴 항목이다. 이 백로그에서는 다루지 않는다.

## 열린 질문

- 클라우드 메타데이터 엔드포인트가 운영 ome 컨테이너에서 닿는지는 배포 사실이라 로컬에서 판정하지 않는다.
