## 3. Background

- 지금 검색은 홈 탭이 받아 온 목록(`PUBLIC_LIST_LIMIT` 100개) 안에서 제목·닉네임·게임 이름을 브라우저가 거른다(#64). 검색창은 홈에만 있다.
- 사용자는 트위치·치지직처럼 검색창을 헤더 가운데에 두고 싶다. 헤더에 있는 검색은 서비스 전체 검색처럼 보이므로, 받아 온 목록만 거르는 지금 방식과 맞지 않는다.
- 공모 원문에는 검색이 필수에도 선택(가산점)에도 없다. 점수에 닿는 길은 "방송 목록" 화면의 완성도뿐이다.
- **발견 결과 (2026-11-15, DISCOVERY-search)**:
  - 로컬 개발 DB에서는 종료 방송이 이미 100개 상한에 걸려 결과가 잘린다. 심사 규모(방송 3~6개)에서는 잘리지 않을 것으로 본다.
  - 그래서 이 규모에서 서버 검색으로 달라지는 점은 결과 범위가 아니다. 지금은 못 내는 결과 종류(스트리머, 게임 별칭, 상태를 가리지 않는 통합 결과)다.
  - 게임 줄임말 10개 중 완전 일치 별칭이 있는 것은 "롤"·"배그"뿐이다. 별칭을 부분 일치로 쓰면 "롤" 하나가 게임 30개에 걸린다.
  - 360px 헤더는 로그인 상태에서 21px만 남는다. 돋보기 버튼(32px + 간격)을 넣으려면 간격을 줄여야 한다.
- 마감은 2026-11-19 23:59 KST이고, 11/19는 신규 기능 금지다. #17(P0 회귀·README)이 아직 열려 있다.

### 도입 판단

1. **지금 겪는 문제**: 헤더로 옮긴 검색이 전체 검색처럼 보이는데, 실제로는 한 탭의 100개 안에서만 거른다. 스트리머를 찾아 채널로 가는 길이 없다. "롤"로 리그 오브 레전드 방송을 찾지 못한다.
2. **대안과 안 쓰는 이유**:
   - 클라이언트 필터 유지: 위 문제를 그대로 둔다. 서버 일정이 밀릴 때의 대체안으로만 남긴다(8.1).
   - `pg_trgm` 인덱스: 부분 일치를 빠르게 하지만 방송 수백 행에는 효과가 없다. 확장 설치 마이그레이션만 는다.
   - Postgres 전문 검색(`tsvector`): 기본 사전에 한국어 형태소 분석이 없다. 단어 일부("리그")로 찾을 수 없다.
   - 외부 검색 엔진(Meilisearch 등): 서버와 색인 동기화를 따로 운영해야 한다. 마감까지 들일 수 없다.
3. **가능해지는 것**: 상태와 다시보기를 가리지 않는 한 번의 검색, 스트리머 결과에서 채널·팔로우로 가는 길, 게임 별칭 검색, 어느 화면에서나 검색.
4. **비용·한계**: 로그인 없이 부르는 엔드포인트가 인덱스 없이 전체를 훑는다. 요청 수 제한으로 막는다. 방송이 수만 개로 늘면 `pg_trgm`이나 검색 엔진이 필요하다. #17에 쓸 시간에서 2.5일을 쓴다.

## 6. Value Proposition(s)

**시청자**
- **Who**: 어느 화면에든 있는 시청자
- **Why**: 아는 스트리머나 게임 방송을 바로 찾고 싶다
- **What before**: 홈으로 돌아가 탭을 고르고, 그 탭의 100개 안에서만 찾는다. 스트리머를 찾아 채널로 가는 길이 없다
- **How**: 헤더 검색창에 "롤"이나 닉네임을 치고 Enter를 누른다. 좁은 화면에서는 돋보기를 누른다
- **What after**: 결과 화면에서 스트리머(채널 링크), 지금 방송, 지난 방송을 한 번에 본다
- **Alternatives**: 치지직·트위치 헤더 검색

**심사자**
- **Who**: 테스트 계정으로 서비스를 둘러보는 공모전 평가자
- **Why**: 방송 목록이 실제 서비스처럼 동작하는지 본다
- **What before**: 홈 탭 안의 필터만 있다
- **How**: README "기능 확인"의 검색 절차를 따른다
- **What after**: 헤더 검색 → 결과 구역 → 시청·채널 이동이 한 흐름으로 확인된다
- **Alternatives**: 없음

## 7. Solution

### 7.1 검색 규칙

- 검색어는 앞뒤 공백을 뺀 뒤 1~50자다. 아니면 400이다.
- 검색어와 대상 문자열을 같은 방식으로 접는다. 공백을 모두 빼고 소문자로 바꾼다(`foldGameText`와 같다). 그래서 "리그오브"가 "리그 오브 레전드"를 찾는다.
- 대상과 일치 방식:

| 대상 | 일치 방식 |
|---|---|
| 방송 제목 | 접은 문자열 부분 일치 |
| 스트리머 닉네임 | 접은 문자열 부분 일치 |
| 방송의 `gameName` | 접은 문자열 부분 일치 |
| 게임 별칭 | 방송의 `gameQid`가 가리키는 `Game.searchText`에 검색어와 **똑같은 토큰**이 있다. 부분 일치는 쓰지 않는다(잡음, 3장) |

- 게임 이름 부분 일치 때문에 "롤"은 "엘더 스크롤" 방송에도 걸린다. 제목 부분 일치와 같은 성질이라 받아들인다. 별칭을 완전 일치로 묶는 이유는 별칭에만 "롤"이 든 게임까지 걸리지 않게 하려는 것이다.

- 방송 설명(`description`)은 찾지 않는다. 결과에 왜 나왔는지 화면에서 보이지 않는다.
- 검색 범위는 공개 목록과 같다. LIVE, 방송 종료, 만든 지 24시간 안의 `READY`다(`READY_LISTED_MS`). 다시보기는 녹화가 있는 방송 종료라서 따로 찾지 않는다.
- `LIKE` 패턴의 `%`·`_`·`\`는 글자 그대로 찾는다(`escapeLike`). `$queryRaw<T>(Prisma.sql`...`)` 형태로 쓴다(채점기 호환).
- 인덱스를 두지 않는다. KR5를 넘으면 `pg_trgm`을 검토한다.

### 7.2 API와 인가

| 행위 | 비로그인 | 로그인 |
|---|---|---|
| `GET /api/search?q=` | 허용 | 허용 |

- 응답:

```ts
{
  streamers: {
    id: string;
    nickname: string;
    avatarUrl: string | null;
    followerCount: number;
    liveBroadcastId: string | null;
  }[];
  broadcasts: BroadcastView[]; // LIVE 먼저, 그다음 READY. startedAt·createdAt 최신 순
  past: BroadcastView[];       // 방송 종료. endedAt 최신 순
}
```

- 스트리머는 닉네임이 맞고, 공개 목록에 방송이 하나라도 있는 사용자다. 방송한 적 없는 시청자 계정은 나오지 않는다(채널 페이지가 비어 있다). 순서는 닉네임 완전 일치 → 앞부분 일치 → 포함, 같으면 팔로워가 많은 순이다.
- 방송·지난 방송은 제목·닉네임·게임 중 하나가 맞으면 나온다. 스트리머로 나온 사람의 방송도 방송 구역에 나온다(치지직과 같다).
- 상한: 스트리머 10, 방송 30, 지난 방송 30. 페이지네이션은 없다. 상한에 닿은 구역에는 화면이 "최근 30개까지 보입니다."를 보인다.
- 요청 수 제한: IP당 1분에 60회(`@nestjs/throttler`, 인증 API와 같은 방식). 넘으면 429다. 자동 완성이 없어 Enter를 누를 때만 부르므로 사람이 닿기 어려운 수다.

### 7.3 화면

- **결과 화면** `/search?q=` (`SearchPage`, 로그인 불필요)
  - 탭 제목은 `'<검색어>' 검색 결과 - Lime`이다.
  - 구역을 위에서부터 "스트리머", "방송", "지난 방송" 순으로 둔다. 빈 구역은 그리지 않는다.
  - 스트리머 항목: 프로필 원(`UserAvatar`), 닉네임, "팔로워 N명", LIVE면 "LIVE" 표시. 누르면 채널 페이지(`channelPath`)로 간다. 넓은 화면은 가로로 늘어놓고, 좁은 화면은 세로 목록이다.
  - 방송·지난 방송: 홈과 같은 `BroadcastGrid`다. 카드의 상태 배지·카테고리 배지·썸네일 규칙이 그대로다.
  - 모두 비면 "'<검색어>'와 맞는 결과가 없습니다."를 보인다. 그 아래에 "지금 방송 중" 구역으로 `GET /api/broadcasts?status=LIVE` 결과를 보인다. LIVE도 없으면 홈 링크만 둔다.
  - 한 번만 읽는다. 홈처럼 30초마다 다시 읽지 않는다.
  - 검색어가 없거나(`/search`) 공백뿐이면 API를 부르지 않고 "검색어를 입력하세요."를 보인다.
- **헤더 검색** (`AppLayout`)
  - 넓은 화면: 로고·메뉴와 계정 메뉴 사이 가운데에 검색창을 둔다(`type="search"`, 화면에 보이지 않는 label "검색", placeholder "방송, 스트리머, 게임 검색", 최대 폭은 새 토큰). `role="search"`인 `<form>`이다.
  - Enter를 누르면 `/search?q=<검색어>`로 **push** 이동한다(뒤로 가기가 이전 화면으로 간다). 공백뿐이면 이동하지 않는다. 결과 화면에서는 검색창에 지금 검색어가 들어 있다.
  - 좁은 화면: 검색창 대신 돋보기 버튼(이름 "검색", 아이콘은 인라인 SVG)을 계정 메뉴 왼쪽에 둔다. 누르면 헤더 줄 전체가 검색 입력줄과 "닫기" 버튼으로 바뀌고 입력칸에 포커스가 간다. Esc와 "닫기"는 원래 헤더로 돌아가고 포커스는 돋보기로 돌아온다. 검색하면 이동하면서 닫힌다.
  - 넓고 좁은 기준 폭은 구현 중 측정(E6)으로 정한다. 360px 로그인 상태에서 들어가도록 헤더 간격을 줄인다(DISCOVERY-search E3).
  - 송출 화면도 같은 헤더다. 송출 중에 검색하면 기존 이탈 확인(#76)이 먼저 뜬다.
- **홈** (`HomePage`)
  - 2단계에서 홈 검색창과 `?q=` 클라이언트 필터를 없앤다. 검색은 헤더 하나로 한다. 탭·카테고리 칩은 그대로다.
  - 예전 `/?q=<검색어>` 주소는 `/search?q=<검색어>`로 `replace` 이동한다.
  - PRD 8.3 시나리오 24의 "홈 검색창에 '리그'"를 "헤더 검색에 '리그'"로 고친다.
- UI 작업 전 `apps/web/CLAUDE.md`를 읽고, 끝나면 그 문서의 "방송 목록" 행과 레이아웃 골격, 화면 표에 결과 화면을 고친다.

### 7.4 Assumptions and open questions

- 결과 화면이 방송 3~6개 규모에서도 완성도로 보인다고 가정한다. 1단계 머지 후 스크린샷으로 판정한다(DISCOVERY-search E5).
- 인덱스 없는 검색이 KR5(200ms)를 지킨다고 가정한다.
- 스트리머를 "공개 목록에 방송이 있는 사용자"로 거르는 것이 테스트 계정 B 같은 시청자 계정을 숨기는 데 충분하다고 가정한다.

### 8.2 첫 버전에서 하지 않는 것

- 자동 완성 드롭다운. 결과 화면의 축소판인데 하루가 든다
