## Product Requirements Document: 방송 준비 중 노출과 채팅·댓글 분리

**Author**: kh.jeon
**Date**: 2026-11-11
**Status**: 구현 완료 (2026-11-11, A #90: #93, B #91: #94, C #92: #95). 송출 중 대기 장면은 하지 않았다

배경 논의: `docs/STRATEGY-chat-replay.md`, `docs/STRATEGY-standby-scene.md`. 이 문서가 두 문서의 결정을 확정한다.

### 1. Summary

방송 전(READY) 방송을 "방송 준비 중"으로 공개 목록에 올리고, 지금 한 목록에 섞인 "댓글"을 방송 중 채팅(`ChatMessage`)과 방송 후 댓글(`Comment`)로 나눈다. 여력이 있으면 다시보기에서 채팅을 재생 위치에 맞춰 흘린다.

### 3. Background

- **방송 전에 모일 곳이 없다**: PRD §7.4는 READY를 공개 목록에서 숨긴다. 시청자는 상세 URL을 알아야 들어오는데, 링크 복사 버튼도 없다. 실제 플랫폼에서 흔한 "시작 전 시청자끼리 채팅" 흐름이 불가능하다.
- **채팅과 댓글이 섞인다**: `Comment` 한 테이블에 방송 중 대화와 방송 후 감상이 함께 쌓인다. 종료 후 들어온 사람이 댓글을 찾기 어렵다. READY에서는 게시판형으로 보여 실시간 대화에 맞지 않는다.
- **채팅 폴링이 비싸다**: LIVE 중 `CommentPanel`이 1초마다 전체 목록을 다시 받는다. 채팅 1,000건이면 1초마다 1,000건이다.
- **다시보기에 현장감이 없다**: Twitch·치지직 다시보기는 재생 위치에 맞춰 채팅을 흘린다. 지금은 녹화 파일별 시작 시각을 저장하지 않아 이 계산이 불가능하다.

왜 지금: 필수·선택 기능이 갖춰졌고 마감(2026-11-19)까지 8일이 남았다. 단, 필수 기능 회귀·README(#17)가 먼저다.

### 4. Objective

시청자가 방송 시작 전부터 목록에서 방송을 찾아 들어와 채팅하고, 방송이 끝나면 댓글과 채팅 기록을 구분해 본다.

**Key Results** (인수 기준으로 대신한다. 공모전이라 사용량 지표가 없다)
- 만든 지 24시간 안의 READY 방송이 공개 목록 "방송 준비 중" 구역에 100% 보이고, 24시간이 지나면 보이지 않는다.
- LIVE 중 채팅 폴링 응답 크기가 전체 건수와 무관하게 새 메시지 수에 비례한다 (1,000건 방송에서 측정).
- ENDED 방송에서 댓글 작성·수정·삭제와 작성자 403이 기존 테스트대로 통과한다 (공모 평가 항목 회귀 0).
- (C) 다시보기에서 재생 위치 ±3초 안의 채팅이 차례로 나타난다.

### 5. Market Segment(s)

- **시청자 (링크 없이 목록으로 들어오는 사람)**: 방송이 곧 시작하는지 알고, 기다리는 동안 다른 시청자와 이야기하고 싶다. 제약: 로그인 없이 보고, 채팅은 로그인 후.
- **스트리머**: 시작 전 시청자를 모으고 싶다. 제약: 송출은 브라우저(PC 화면 공유, 휴대폰 카메라).
- **공모전 심사자**: 댓글 CRUD(선택 기능)와 방송 상태 관리(필수)를 확인한다. 제약: README 절차대로만 본다.

### 6. Value Proposition(s)

**시청자 — 방송 준비 중**
- **Who**: 목록을 둘러보는 시청자
- **Why**: 곧 시작할 방송을 미리 찾아 기다리고 싶다
- **What before**: READY 방송은 목록에 없다. 링크를 받아야만 들어온다
- **How**: 목록 "방송 준비 중" 구역 → 대기 이미지(없으면 검은 화면) + "방송 준비 중입니다" + 채팅
- **What after**: 시작 전부터 채팅하며 기다리고, 송출이 시작되면 자동으로 재생된다
- **Alternatives**: 링크 공유(스트리머가 직접 퍼뜨려야 함)

**시청자 — 채팅과 댓글**
- **Who**: 방송 중·후에 들어온 시청자
- **Why**: 방송 중엔 빠르게 대화하고, 끝난 뒤엔 감상을 남기거나 읽고 싶다
- **What before**: 두 가지가 한 목록에 섞인다
- **How**: READY·LIVE는 채팅, ENDED는 "채팅 기록 / 댓글" 탭
- **What after**: 원하는 쪽만 본다. (C) 다시보기에서 채팅이 장면에 맞춰 흐른다
- **Alternatives**: 시간순 목록을 직접 훑기

### 7. Solution

#### 7.1 A. 방송 준비 중 노출

- 공개 목록 API가 READY 중 `createdAt`이 24시간 안인 것을 포함한다. 순서는 LIVE → READY → ENDED. Prisma enum 선언 순서가 READY → LIVE → ENDED라서 지금 `orderBy: status asc`로는 READY가 맨 앞에 온다. 순서를 따로 정한다.
- 화면 문구: 배지 `READY` = "방송 준비 중" (`StatusBadge`), 시청 화면 안내 = "방송 준비 중입니다." 송출이 시작되면 자동 재생은 지금 그대로.
- 목록 필터 탭에 "방송 준비 중" 추가.
- 팔로우 목록은 지금처럼 LIVE만.
- 자동 종료·자동 삭제는 하지 않는다. 24시간이 지난 READY는 공개 목록에서만 빠지고 "내 방송"에는 남는다.
- PRD §7.4 "목록 노출"과 어긋난다. PR 본문에 적고 PRD·`GLOSSARY.md`(READY 정의: "소유자에게만 보인다")를 고친다.

#### 7.2 B. 채팅·댓글 분리

- 새 `ChatMessage` 테이블(`id`, `broadcastId`, `authorId`, `body`, `createdAt`, 인덱스 `(broadcastId, createdAt)`). 수정 없음이라 `updatedAt` 없음. `Comment`는 그대로.
- API
  - `GET /broadcasts/:id/chat?after=<id>`: 공개. `after` 이후만, 오래된 순.
  - `POST /broadcasts/:id/chat`: 로그인. READY·LIVE에서만, ENDED면 409. 본문 1~200자.
  - `DELETE /chat/:messageId`: 작성자만 (다른 사용자 403).
  - 댓글 `POST /broadcasts/:id/comments`: ENDED에서만, 그 전이면 409. 조회·수정·삭제는 지금 그대로.
- 기존 데이터: 마이그레이션 SQL로 방송의 `endedAt` 이전(또는 방송이 아직 끝나지 않은)에 쓴 `Comment` 행을 `ChatMessage`로 옮긴다. `endedAt` 이후 행은 `Comment`에 남는다.
- 화면: READY·LIVE는 채팅 패널(1초 커서 폴링). ENDED는 "댓글"(기본) / "채팅 기록"(읽기 전용) 탭.
- 문서: PRD §6 인가 매트릭스에 채팅 줄, README "기능 확인"에 "끝난 방송 → 댓글 탭에서 작성·수정·삭제", 시드에 끝난 방송 1개.

#### 7.3 C. 다시보기 채팅 동기화 (B 다음, 여력이 있으면)

- 스파이크(2시간): OME 녹화 info XML(`InfoPath`)에 파일별 시작 시각이 있는지 확인. 없으면 Admission Webhook 허가 시각을 연결마다 기록해 파일과 짝짓는다.
- 녹화 파일별 시작 시각을 저장하고 다시보기 API에 함께 내려준다.
- "채팅 기록" 탭이 다시보기 재생 중 `timeupdate`로 `createdAt − 파일 시작 − 3초 ≤ 재생 위치`인 채팅만 보인다. 탐색하면 즉시 다시 거른다. READY 채팅은 0초, 끊김 공백 중 채팅은 다음 파일 0초.

#### 7.4 Assumptions and open questions

- (가정) 공모전 규모에서 방송당 채팅은 수천 건 이하라 Postgres 한 테이블과 클라이언트 필터로 충분하다. NoSQL은 쓰지 않는다.
- (가정) 심사 기간에 버려진 READY가 쌓여도 24시간 필터로 목록이 지저분해지지 않는다.
- (열림) 스트리머가 자기 방송의 남의 채팅을 지울 수 있게 할지. 1차는 작성자 본인만.
- (열림) C의 시작 시각 출처. 스파이크로 정한다.
