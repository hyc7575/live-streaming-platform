## Product Strategy: 방송 썸네일과 대기 화면 (Lime 부가기능)

**Date**: 2026-11-10
**Stage**: MVP (필수·선택 기능 구현 완료, 마감 2026-11-19 23:59 KST)
**Author**: kh.jeon

> 결과: 목록 카드 기본 그림·방송 준비 중 안내·경과 시간(#61), 캡처 썸네일(#62), 기본 대기 이미지(#63)로 구현했다. 후속 논의는 `STRATEGY-chat-replay.md`다.

> 범위: 회사 전략이 아니라 공모전 제출물 안의 기능 묶음 전략이다. 9절 중 Growth Engine·Defensibility는 공모전 맥락에서 거의 의미가 없어 짧게 둔다.

### 1. Vision

링크를 받은 사람이 목록과 시청 화면만 보고도 "지금 무슨 방송이 하고 있는지, 언제부터 했는지"를 바로 알게 한다. 빈 회색 카드와 검은 화면을 없앤다.

### 2. Target Segments

| Segment | Pain Level | Current Alternative | Priority |
|---|---|---|---|
| 공모전 심사자 | 높음. 목록 카드가 빈 회색 박스라 미완성처럼 보인다 | 제목·상태 배지만 보고 판단 | 1 |
| 시청자 (링크로 들어옴) | 중간. 방송 전에 들어오면 검은 화면 + "불러오는 중" | 새로고침 | 2 |
| 스트리머 | 낮음~중간. 방송 전 화면을 꾸밀 방법이 없다 | 없음 | 3 |

**Primary segment**: 심사자. 평가 기준이 "필수 기능 완성도 우선"이고, 방송 목록·상세는 필수 요구사항(공모 원문 2-3)이다. 썸네일은 그 필수 화면의 완성도를 올린다.
**Explicitly not serving**: 방송을 미리 잡아 두고 알림을 받으려는 사용자. 방송 예약·팔로우·알림은 PRD §8.2 Non-goal이다.

### 3. Pain Points & Value Created

- **목록 카드가 비어 있다**: `BroadcastGrid`의 `.thumbnail`은 배지만 있는 빈 박스다. 실제 장면이 보이면 "실제로 송출되는 서비스"라는 인상을 준다.
- **방송 전 시청 화면이 검은 화면이다**: READY 방송에 들어오면 무엇을 기다리는지 알 수 없다. 대기 이미지와 안내가 있으면 시청자가 머문다.
- **방송이 얼마나 됐는지 모른다**: `startedAt`이 이미 있는데 화면에 쓰지 않는다.

### 4. Value Propositions

- **심사자**: When 목록 화면을 처음 열 때, they want 각 방송이 무엇인지 한눈에 보고 싶어 한다, so they can 실제 서비스 수준인지 빠르게 판단한다.
- **시청자**: When 방송 시작 전에 링크로 들어왔을 때, they want 방송이 곧 시작한다는 걸 알고 싶어 한다, so they can 창을 닫지 않고 기다린다.
- **스트리머**: When 방송을 만들 때, they want 대기 이미지를 정하고 싶어 한다, so they can 방송 전에도 자기 방송처럼 보이게 한다.

### 5. Strategic Trade-offs

| We Choose | Over | Because |
|---|---|---|
| 송출 브라우저가 미리보기에서 프레임을 캡처해 올리는 썸네일 | OME 내장 썸네일(`Encodes`의 Image) | OME 썸네일은 서버가 영상을 디코딩한다. PRD는 VPS CPU 때문에 트랜스코딩을 뺐고(§8.2), 스파이크 기준 2가 "CPU가 낮게 유지"다. 브라우저 캡처는 서버 CPU를 쓰지 않는다 |
| 방송 경과 시간(LIVE 후 `startedAt`부터) | 시작 카운트다운 | 카운트다운에는 예정 시각이 필요하고, 그건 PRD §8.2 Non-goal인 "방송 예약"이다. 경과 시간은 이미 있는 데이터로 된다 |
| 업로드 파일을 디스크 볼륨에 두고 Caddy가 내주기 | DB bytea, 외부 스토리지(S3 등) | 녹화가 이미 같은 방식(`/recordings`, Vite proxy·Caddy)이라 운영 경로가 하나 늘 뿐이다. 외부 스토리지는 계정·키·비용이 늘어난다 |
| 이미지 형식·크기 검사만(JPEG·PNG·WebP, 2MB, 매직 바이트) | 서버 리사이즈(`sharp`) | 새 네이티브 의존성과 빌드 부담. 브라우저 캡처는 크기를 클라이언트가 정한다 |
| 공유 링크 복사 버튼 | 시청자 수 표시 | 링크 복사는 "누구나 로그인 없이 시청"을 바로 보여 준다. 시청자 수는 OME 통계 API 프록시와 폴링이 더 든다 |

### 6. Key Metrics

공모전이라 사용량 지표가 없다. 인수 기준으로 대신한다.

- **North Star**: 목록에서 LIVE·방송 종료 카드 100%에 이미지가 보인다 (캡처나 대기 이미지, 없으면 기본 그림)
- **Input**: LIVE 썸네일 갱신 주기 30초 이내 / 대기 이미지 업로드 성공 / READY 시청 화면에 대기 화면 표시
- **Health (guardrail)**: 송출 중 썸네일 업로드가 송출 비트레이트·프레임에 영향 없음, VPS CPU 변화 없음, 업로드는 소유자만(403 테스트), 방송 삭제 때 이미지도 삭제

### 7. Growth Engine

해당 없음(공모전 제출물). 대신 "심사자 동선": README 기능 확인 절차에 썸네일·대기 화면 확인 단계를 넣어 심사자가 직접 보게 한다(T13).

### 9. Defensibility

해당 없음. 대신 면접·심사에서 설명할 수 있는 설계 이유가 남는다: 서버 CPU 한계 때문에 썸네일 생성을 송출 브라우저로 옮긴 결정.

### Strategic Risks

1. **마감 일정**: 남은 일이 #56(플레이어), #17(실기기 회귀·README), #8·#45(서버·운영)다. 이 기능은 필수 기능보다 뒤다. → 1단계(경과 시간·링크 복사·기본 그림)만 해도 효과가 있게 나눈다.
2. **업로드 보안 면**: 파일 업로드는 새 공격 면이다. → 소유자 인가, 매직 바이트 검사, 서버가 정한 파일명, `X-Content-Type-Options: nosniff`, 크기 상한.
3. **모바일 송출 부하**: 휴대폰에서 캡처·업로드가 송출을 방해할 수 있다. → 30초 간격, 작은 해상도(가로 480px) JPEG, 실기기 확인.
